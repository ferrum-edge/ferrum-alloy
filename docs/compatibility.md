# Compatibility

This page records the supported pairing and its qualification limits. The v0.9.14/v0.9.13 adoption candidate requires fresh hosted CI on its exact commit; the earlier v0.9.12/v0.9.11 window and its CI history are historical. Coverage listed below describes the existing gates, not a green result for this new commit. Edge's broader protocol support, such as HTTP/3, gRPC, and mesh modes, does **not** imply Alloy support.

The same pairing in machine-readable form is in [compatibility.json](compatibility.json).

## Supported Edge releases

Alloy supports **the latest Ferrum Edge release and the release before it**. CI reads `edge_support.tested` from [compatibility.json](compatibility.json) and runs the `Ferrum Edge end-to-end` and `Generated Edge configuration validates` jobs once for each release below, named `(baseline)` for the first row and `(previous)` for the second. The first row is the contract baseline above; the demo stack uses it unless `EDGE_IMAGE` is set.

The published v0.9.14 and v0.9.13 image digests are recorded in the table
above. Their publication and signature evidence does not qualify Alloy's new
pairing; fresh hosted validation is still required. The support window rolls
forward under the existing policy; no additional release-window restriction
is introduced.

- **Existing Alloy wire behavior.** The supported v0.9.14 and v0.9.13 releases retain the CLIENT span per backend attempt (Edge #5864, #5867, #5875) and hand Alloy that span, not the SERVER span, as the `traceparent` parent, so Alloy's SERVER span is a grandchild of the Edge SERVER span; the `traceparent` Edge echoes to the client still names the SERVER span. Earlier v0.9.8 input has the Alloy span directly under the Edge SERVER span. Alloy's OTLP import and diagnosis rules link a service span to the gateway request through at most one Edge attempt span, and the end-to-end checks accept both shapes. Diagnosis interprets each attempt span's duration and connection attributes.
- v0.9.14 and v0.9.13 treat the whole `x-consumer-*` request namespace as gateway-owned (Edge #5880): a client's `X-Consumer-Role` no longer reaches the service. Earlier v0.9.8 stripped only `X-Consumer-Username` and `X-Consumer-Custom-Id`. Alloy trusts only those two names, and only from a verified gateway identity.
- v0.9.14 and v0.9.13 read the `x-ferrum-mcp` OpenAPI extension on `POST /api-specs` and publish the selected operations as MCP tools (Edge #5930). Earlier v0.9.8 accepts the same document and ignores the extension. The `edge-config` job submits the exported agent-tool fixture to both supported releases and checks each outcome ([AI-agent tools](agent-tools.md)).
- v0.9.14 and v0.9.13 can stamp an opaque `X-Ferrum-Diagnostic-Ref` on gateway-authored responses (off by default with `FERRUM_DIAGNOSTIC_REFS`) and strip a backend copy. Alloy never emits it. Diagnosis records a reference a client observed (rule `alloy.r007`, at most `likely`). Only an explicit admin lookup bound to a separate trusted capture under ADR 0009 can confirm that record's facts; service reports and timing remain unverified. The end-to-end stack turns references on with the admin listener off and confirms nothing.
- v0.9.14 and v0.9.13 refuse `;` path parameters unless a proxy sets `allow_path_parameters`, and refuse empty and `;` dot segments. `ferrum-alloy edge export` never sets the field, and manifest validation refuses paths either supported release would refuse.
- The `X-Gateway-Error` vocabulary is the same eight tokens in v0.9.14 and v0.9.13, and both strip backend-supplied copies of `X-Gateway-Error` and `X-Gateway-Upstream-Status`. v0.9.14 improves internal classification of backend HTTP/2 resets without adding a token. A response header names no Edge version, so `backend_timeout` keeps the broader meaning releases before v0.9.8 gave it (a backend or route deadline elapsed), and a header alone never exceeds `likely`.
- The v0.9.11 source changes TLS material-selector validation and internal transport/auth-lifetime handling, without changing the existing fields or `x-ferrum-mcp` shape Alloy exports. The new admin snapshot/verification/egress contracts are not called by Alloy; its G01 schema, lookup and authority boundary remain unchanged. The [inventory re-audit](edge-contract-inventory.md#revisions-inspected) records the inspected files.
- The v0.9.12 source adds admin-only deployment snapshots and dependency-fenced partial mutations (Edge #6012). Canonical ETag/If-Match descriptions now include that opt-in profile. Alloy does not call it or adopt its new schemas/fixtures; the data-plane headers, telemetry, identity, G01 lookup and generated resource shapes were unchanged from v0.9.11.
- Edge v0.9.13 adds an early route-total deadline for uploads (Edge #6024), reported with `rejection_phase = "route_request_timeout_early_upload"`. Alloy records it as pre-upstream admission evidence. The same release adds a pure preview of route-total deadlines and concrete-type checks for built-in plugin declarations; these do not add wire headers or telemetry fields.
- Edge #5954 changes MCP input handling in v0.9.10: `ai_prompt_shield` refuses non-UTF-8 declared charsets and uninspectable JSON-RPC bodies in enforcing modes, while `mcp_gateway` rejects non-UTF-8 charsets and fails closed on uninspectable or over-nested batches. These MCP request checks do not change Alloy-consumed headers, tracing, telemetry, identity, error tokens, or generated Edge configuration contracts.
- **Unsupported releases.** Older releases and unreleased Edge `main` are not tested. Alloy does not refuse to run behind them, but nothing in the inventory is claimed for them. Diagnosis treats their tokens and attributes by the same rules: an unknown `X-Gateway-Error` token yields `unknown`, never a guessed meaning.
- **New releases.** `.github/workflows/edge-bump.yml` checks for a new Edge release every day. When it finds one, it resolves the tag's multi-arch index digest, verifies with Cosign that Edge's release workflow signed that digest for the tag and its source commit (the run fails otherwise), and opens a draft pull request that makes the new release the baseline, keeps the previous baseline as the second supported release, and drops the oldest. The same CI jobs then prove or disprove compatibility. Its pull request still needs the re-audit below before it merges.

## Topology tested end to end

```text
client ──HTTP/1.1──▶ Ferrum Edge ──HTTPS + mTLS (SPIFFE SVID-style client cert)──▶ Alloy ──▶ simulated dependency
                      │  OTLP/HTTP JSON                                              │  OTLP/HTTP protobuf
                      └────────────────────────▶ OpenTelemetry Collector ◀───────────┘
```

| Leg | Protocol observed |
|---|---|
| Client → Edge | HTTP/1.1, plaintext, port 8000 |
| Edge → Alloy | HTTPS. Alloy spans recorded `network.protocol.version = 2`, so Edge negotiated HTTP/2 through ALPN. |
| Direct client → Alloy (bypass check) | HTTPS, HTTP/1.1, no client certificate → `403 gateway-required` |
| Edge → Collector | OTLP/HTTP **JSON** (`POST /v1/traces`) |
| Alloy → Collector | OTLP/HTTP **protobuf** (`POST /v1/traces`) |
| Trust mode | `gateway_required`; `trust.identities = ["spiffe://ferrum.demo/ns/edge/sa/gateway"]`; `server.tls.client_auth = optional` |
| Edge connection pool | `FERRUM_POOL_WARMUP_ENABLED=false`, `FERRUM_POOL_HTTP2_CONNECTIONS_PER_HOST=1`, so connection identity is deterministic. Edge's defaults are not exercised. |
| Edge diagnostic references | `FERRUM_DIAGNOSTIC_REFS=errors` (Edge's default is `off`). Both supported releases stamp `X-Ferrum-Diagnostic-Ref` on gateway errors. The admin listener stays off, so nothing is looked up. |

What that job verifies is listed in [ADR 0007](adr/0007-real-gateway-integration-testing.md). The first local run passed the original 19 checks. The attempt and connection cases below were added afterwards and are verified by CI, bringing the job to 48 named checks. The two diagnostic-reference checks run on both supported releases.

### Attempt and connection cases

Both supported releases run every case. The driver resolves the release under test from `EDGE_IMAGE` (set by CI per matrix row) against `compatibility.json`, or the baseline when it is unset, and the retry case requires that release's attempt-span shape, so a swapped image or a changed shape fails. The extra proxies come from `gen-e2e-edge-config`, which appends them to the unchanged `ferrum-alloy edge export` output, and every fault is produced inside the compose network.

| Case | How it is produced | What is checked |
|---|---|---|
| Retry | Alloy's `/flaky/{key}` fails the first attempt with `503`; proxy `e2e-retry` retries `503` once (`retry` block, default 100 ms backoff). | The supported releases produce two Alloy SERVER spans under the same Edge SERVER span (`503`, then `200`), each through its own attempt span numbered `1` and `2`; Edge `backend_ttfb` is at least both attempts' time to headers plus the backoff. Diagnosis reports `alloy.gateway.multiple_service_attempts`, makes no gateway-wide comparison, confirms nothing, and scopes values to attempts `1` and `2`. For legacy v0.9.8 input, the same service spans are direct children of the Edge SERVER span, with no attempt scope. |
| Cold and reused connection | Proxy `e2e-reuse` uses the `alloy-reuse` alias; Alloy counts every request per connection on every route, and `/conn` reports how many earlier requests its connection carried. | The first request's connection carried no earlier request, and a later one reused one. Neither request's SERVER spans carry a connection-setup value. On v0.9.14 and v0.9.13 a setup Edge measured appears only on the attempt span, scoped to the attempt, and never on the reused request; an unattributed interval cites that setup or the reuse, or lists setup timing as missing. |
| Concurrent HTTP/2 streams | Six concurrent requests through `e2e-reuse`; Alloy's `/gather/6` waits until all six are in the handler. | Six overlapping Alloy SERVER spans over HTTP/2, each under its own Edge span, on fewer than six connections, with no setup charged to any stream. |
| Client cancellation mid-body | The driver closes its connection after the first frame of a 4 s event stream. | Edge records the client disconnect; one Alloy SERVER span with outcome `cancelled`, ended mid-stream, and one `alloy.response.body_incomplete` finding. |
| Refused connection | Proxy `e2e-refused` targets a port on the Alloy container with no listener. | `X-Gateway-Error: connection_failure`, an Edge span with `gateway.error.class` and no Alloy span, and a `likely` diagnosis that does not claim the service is down. On both supported releases the response also carries a well-formed `X-Ferrum-Diagnostic-Ref`, which diagnosis records as `alloy.edge.diagnostic_ref`, `likely`, with nothing confirmed. |

Not covered: an upstream reset after a connection is established, and per-attempt timing on v0.9.8, which does not record it. Retry backoff is not measured on either release (see [measurement-semantics.md](measurement-semantics.md#ferrum-edge-measurements-supported-v0914-and-v0913-legacy-v098-input)).

## Semantic conventions

- HTTP span and metric attribute names follow the **stable** OpenTelemetry HTTP conventions: `http.request.method`, `http.route`, `http.response.status_code`, `url.scheme`, `network.protocol.version`, `error.type`, `server.address`, `server.port`, and the optional `url.path`, `client.address`, `user_agent.original`.
- Database operations use `db.system.name`, `db.operation.name`, and `db.query.summary` from the database conventions, which are not all stable.
- The Prometheus histogram `http_server_request_duration_seconds` (OpenTelemetry `http.server.request.duration`) uses Alloy's documented boundaries: middleware entry to body finalization.
- Alloy-specific data uses the `alloy.*` prefix.
- **No `schema_url` is emitted.** Ferrum Edge v0.9.14 and v0.9.13 emit none either, and its `http.route` holds the proxy name, not a template.

## Pairing rules

- Moving to a new Edge release requires:
  1. updating the image digest in `compatibility.json` (`edge` and `edge_support.tested`, which is CI's Edge matrix), `examples/edge-observability/Dockerfile` (`EDGE_IMAGE` default), and this page;
  2. updating `ferrum_alloy_edge::contract::{EDGE_RELEASE, EDGE_SOURCE_COMMIT}`, the headers of `contracts/fixtures/manifests/*.edge.yaml` (`UPDATE_SNAPSHOTS=1`), and the release the CLI test expects;
  3. re-auditing the contract inventory (checklist below);
  4. passing the `Ferrum Edge end-to-end` and `Generated Edge configuration validates` jobs for every supported release.
- The canonical pin must match the baseline release: adopt the same 16 files from the matching published `contracts-edge-*` tag, verify every byte/hash, and update local adoption metadata. The unchanged report retains its original shared-freeze tag separately.
- `crates/ferrum-alloy-edge/tests/pairing.rs` fails when steps 1 and 2 disagree, when the window is not two releases led by the baseline, when `ci.yml` stops reading its Edge matrix from `compatibility.json` or pins an Edge image itself, or when `contract::GATEWAY_ERROR_TOKENS` and the diagnostics catalog differ.
- Unreleased Edge main is never pinned.

### Re-audit checklist

Run it against the new release's tag in the Edge repository, and record the result in the revision table of [edge-contract-inventory.md](edge-contract-inventory.md). Last static inspection: `v0.9.12..v0.9.13` and `v0.9.13..v0.9.14` on 2026-10-08, recorded item by item there; hosted adoption validation remains pending. The currently supported window is v0.9.14 and v0.9.13; older release references below describe historical behavior.

1. `git diff <old-tag> <new-tag> --stat -- src/plugins/otel_tracing.rs src/plugins/correlation_id.rs src/config/types.rs src/proxy/headers.rs src/retry.rs`. An unchanged file keeps its entries; re-read every entry backed by a changed file.
2. `src/retry.rs`: the `X-Gateway-Error` vocabulary (`HTTP_OBSERVABILITY_ERROR_CLASSES`). Mirror additions in `contract::GATEWAY_ERROR_TOKENS`, `catalog::EDGE_GATEWAY_ERROR_TOKENS`, and the `does_not_prove` list of rule `alloy.r007`, and state what each new token does not prove. Never narrow an existing token's meaning: a header names no Edge version. Bump `contracts/ferrum-contracts/PIN` to the matching `contracts-edge-*` tag and re-verify the vendored vocabularies (see [contracts/README.md](../contracts/README.md#ferrum-contracts-pin)); their release-specific meanings are recorded in the pairing test, never rendered.
3. `src/proxy/headers.rs`: which gateway-owned response headers are stripped from backend responses, and which request headers Edge overwrites.
4. `src/plugins/otel_tracing.rs`: span kinds, `gateway.*` attribute names and meanings, and `traceparent` parsing. New timing fields go through `measurement-semantics.md` and `catalog.rs` first.
5. `src/plugins/correlation_id.rs`: the accepted request-id grammar (mirrored in `ferrum-alloy-telemetry`).
6. `src/config/types.rs` and the `otel_tracing` `ALLOWED_CONFIG_KEYS`: every field `ferrum-alloy edge export` writes (the `edge-config` job validates the fixture).
7. `docs/plugin_execution_order.md` and the `rejection_phase` values: `catalog::EDGE_PRE_UPSTREAM_PHASES`.
8. `src/plugins/mod.rs` and `src/proxy/headers.rs` (`is_consumer_assertion_header`, added in v0.9.9): the reserved `x-consumer-*` names stripped from clients.
9. Entries marked UNAVAILABLE: check whether the release now produces them. A new contract stays PROPOSED here until it is verified in a release.

# Release readiness

Alloy is distributed from Git only. No Alloy crate is published to any registry, and every crate is `publish = false`. This page records that [distribution decision](#distribution-decision), what CI already checks, the checklist a release commit must satisfy, and the [deferred registry decisions](#deferred-registry-decisions) that must be settled if the owner ever revisits it.

The [implementation ledger](implementation-status.md#release-candidate-tracker) records the current #28 status. Packaging and the checklist shipped in #59, and the owner recorded the Git-only decision for #24 on 2026-10-29. Shared hosted benchmark preparation does not fulfill #15/#16's dedicated acceptance. Shared contract qualification and the fresh hosted qualification the `contracts-edge-0.9.17` adoption still needs before root decides #27/#28 are recorded in the [owner/adoption record](shared-contract-qualification.md). Canonical publication grants no separate Alloy crate publishing approval or performance acceptance. These remaining gates require separate evidence or decisions before declaring release readiness.

## Distribution decision

**Decision (owner, 2026-10-29): Git-only for now** ([#24](https://github.com/ferrum-edge/ferrum-alloy/issues/24)).

- No Alloy crate is published to crates.io or to any other registry. Every crate keeps `publish = false`.
- The license is unchanged: PolyForm Noncommercial 1.0.0, with commercial licensing in `LICENSE-COMMERCIAL.md`. Vendored Swagger UI keeps its own terms.
- Consumers depend on Alloy by git branch, tag, or revision, or by path, as [getting started](getting-started.md) describes. `ferrum-alloy new` keeps writing a git dependency, on branch `main` by default, or a path dependency with `--alloy-path`.
- The `Package dry run` job stays. It keeps the crates packageable so that a later registry decision does not start from scratch, and it never uploads anything.

This decision does not authorize publishing, creating registry accounts or API tokens, reserving names, or changing the license. A Git release is a tag on a commit that satisfies the [release checklist](#release-checklist), with its release notes in a GitHub release for that tag; tagging still needs the owner's approval.

Revisiting the decision is a new owner decision. It requires every item under [deferred registry decisions](#deferred-registry-decisions), and every registry release, not only the first, must complete the checklist items marked *registry only*.

## What CI checks now

The `Package dry run` job in `.github/workflows/ci.yml` runs on every pull request and every push to `main`. `cargo package` only builds `.crate` archives under `target/package/`; it never uploads anything.

1. **Package.** `cargo package --locked --no-verify --exclude-lockfile` for the five crates: `ferrum-alloy-diagnostics`, `ferrum-alloy-telemetry`, `ferrum-alloy-edge`, `ferrum-alloy`, and `ferrum-alloy-cli`. The examples are not packaged.
2. **Packaged files.** Every archive contains `Cargo.toml`, `README.md`, `LICENSE`, and `LICENSE-COMMERCIAL.md`, and the license files match the repository's byte for byte. The CLI archive contains every committed file under `crates/ferrum-alloy-cli/templates/`, including `templates/base/.github/`, and the `ferrum-alloy` archive every committed file under `crates/ferrum-alloy/assets/`.
3. **Packaged sources build on their own.** The job unpacks the archives into a new workspace outside the repository, with a `[patch.crates-io]` entry that points each crate at its unpacked archive, and runs `cargo check` with all features and with default features. It fails if any `ferrum-alloy*` crate resolves from a registry instead of the unpacked archives. This catches a file a crate needs but does not package, such as a template compiled in with `include_str!`.
4. **Container images.** The repository does not publish a container image. The `Ferrum Edge end-to-end` job builds the example stack's images from `examples/edge-observability/Dockerfile` and its compose file; keep that build passing when those inputs change.

The `Package dry run` job name is a stable CI check. Extend that job if more publishable crates are added; do not create a second packaging job.

### Why `--no-verify --exclude-lockfile`

The crates depend on each other, and none of them is in a registry. `cargo package` writes a `Cargo.lock` into each archive and, unless `--no-verify` is given, builds each archive; both resolve the sibling crates. Packaging with a lockfile or with verification needs a registry the crates may be published to, and `publish = false` rules that out: Cargo resolves workspace siblings through a temporary local registry, but it does not add `publish = false` packages to it, so it would look for them on crates.io and fail (or, if someone published a crate with the same name, resolve to that crate). `--exclude-lockfile` and `--no-verify` skip both resolutions. Step 3 then does the verification that `--no-verify` skips, with an explicit patch that can never resolve to a registry crate.

Once publishing is approved and `publish = false` is removed, `cargo package --workspace` resolves the siblings through its local registry, and the job can drop both flags.

### Package contents

Each crate declares an `include` list in its `Cargo.toml`: `src/`, its `README.md`, and the two license files; the CLI also includes `templates/`, and `ferrum-alloy` includes `assets/`, the vendored documentation UI (feature `openapi-ui`) with its Apache-2.0 `LICENSE`, `NOTICE`, bundled notices, and hash manifest. Tests are not packaged, because they read fixtures from outside the crate (`contracts/`, `docs/`, the examples). The `LICENSE` and `LICENSE-COMMERCIAL.md` files in each crate directory are symbolic links to the repository's, and Cargo packages their contents.

The internal workspace dependencies carry `version = "0.1.0"` next to `path`, so that the packaged manifests contain a registry dependency on each sibling. Builds in this repository still use the path.

## Release checklist

A release commit must satisfy every item. Record the evidence in the release notes. Under the [Git-only decision](#distribution-decision), a release is a Git tag and the items marked *registry only* do not apply. They apply to every registry release; their one-time configuration changes (removing `publish = false`, dropping the package flags, the license exceptions, and the manifest license expression) are made by the first.

- [ ] **Owner approval.** The owner has approved this release. For a registry release, the [deferred registry decisions](#deferred-registry-decisions) are also recorded.
- [ ] **Version.** All five crates share `workspace.package.version`. Bump it and the `version` of every internal entry in `[workspace.dependencies]` together. Before 1.0, a breaking change bumps the minor version, and any other change bumps the patch version.
- [ ] **Changelog.** [CHANGELOG.md](../CHANGELOG.md) lists the user-visible changes, including changes to configuration (`docs/configuration.md`), the diagnostic evidence schema, and Edge contracts. Review its Unreleased entries and create the release entry for the approved version.
- [ ] **MSRV.** The release notes state the MSRV (`rust-version`, currently 1.94, set by sqlx 0.9), and the `MSRV (1.94)` job passes on the release commit. An MSRV increase is called out as a change.
- [ ] **Compatibility.** `docs/compatibility.md` and `docs/compatibility.json` describe the tested matrix on the release commit: the Edge support window (the latest Edge release and the previous one), the pinned images, and the component versions.
- [ ] **Edge contract pin.** If the Edge contract baseline changes, `contracts/ferrum-contracts/PIN` names the matching published `contracts-edge-*` tag and commit, its file hashes match the vendored files, and the pairing checks pass. Update `docs/compatibility.json`, the compatibility page, `contract::{EDGE_RELEASE, EDGE_SOURCE_COMMIT}`, fixture headers, and the CLI pairing assertion together. See [compatibility](compatibility.md#pairing-rules) and [the contract pin procedure](../contracts/README.md#ferrum-contracts-pin).
- [ ] **Security review.** Review the release diff against [the security model](security.md), including dependency changes and security-relevant behavior. Record the reviewer and evidence with the release notes; resolve or explicitly disposition findings before release.
- [ ] **Benchmark baseline.** A benchmark run for the release commit is recorded as [benchmarks](benchmarks.md) describes, with its host and limits. No regression budget exists yet (#15), so the baseline is evidence, not a gate.
- [ ] **CI evidence.** Every job in `.github/workflows/ci.yml` passed on the release commit itself, including `Package dry run`, both `Ferrum Edge end-to-end` slots, `Generated projects`, `PostgreSQL integration`, `Dependency policy`, `MSRV`, and `Fuzz smoke`. Link the run in the release notes.
- [ ] **SBOM and provenance.** Generate an SPDX or CycloneDX SBOM for the exact release commit and attach it to the tag's GitHub release. When the release ships build artifacts (for a registry release, the `.crate` archives), also produce build provenance from the trusted CI workflow for that same repository, ref, and commit, verify that its subject digests match the released artifacts, and link it from the release notes. A Git release without build artifacts has no provenance subject. Do not claim an attestation that was not produced and verified.
- [ ] **Generated projects.** `ferrum-alloy new` writes a git dependency on Alloy that follows `main` by default (`--alloy-git`, `--alloy-branch`, `--alloy-tag`, or `--alloy-rev` change it). The release notes show `ferrum-alloy new <name> --alloy-tag <tag>` for a starter pinned to this release. For a registry release only, decide whether starters switch to a registry dependency, and update the templates and the generator tests if so.
- [ ] **License policy** (*registry only*). `cargo deny check` skips the five crates' own `PolyForm-Noncommercial-1.0.0` license only while they are private: `[licenses.private] ignore` in `deny.toml` skips a crate whose `publish` is `false` (or an empty list), or lists only registries that `[licenses.private] registries` also names. A crate published to crates.io or another public registry is not private, so in the first registry release PR add a license exception for each of the five crates. Only for a private alternate registry can the crates instead set `publish = ["<registry>"]` and list the same name under `[licenses.private] registries`; setting `registries` alone, with `publish` removed, is not enough. In the same PR, give `ferrum-alloy` its own `license`, overriding `license.workspace` for that crate only, with the expression recorded under [deferred registry decisions](#deferred-registry-decisions), so its manifest does not claim the vendored Swagger UI files are PolyForm-licensed.
- [ ] **Merge and tag.** The release commit is a GitHub merge commit whose second parent is the reviewed PR head. Confirm the `push` CI run for that merge commit is green before creating the release tag. Tag that merge commit itself, never the PR head or a commit that has not passed push CI; record the tag and CI run in the release notes.
- [ ] **Publish** (*registry only*). In the release PR, remove `publish = false` (or restrict it to the chosen registry) and drop `--no-verify --exclude-lockfile` from the package job, so that push CI on the merge commit packages exactly what will be published. Publish only after **Merge and tag**: from a Linux or macOS checkout (`core.symlinks=true`) of the tagged merge commit whose push CI, including `Package dry run`, passed; a Windows checkout turns the symlinked license files into 13-byte text files. Check that each packaged `LICENSE` matches the root file before `cargo publish`, and publish in dependency order: diagnostics, telemetry, edge, `ferrum-alloy`, the CLI. A published version cannot be replaced, so never publish from a PR head or an untagged commit.

## Deferred registry decisions

The Git-only decision sets these aside; it does not settle them. Each one must be decided and recorded here before any registry publication. The evidence below was refreshed on 2026-10-29. It is research, not legal clearance or a name reservation.

- **Crate and command names, and registry availability.** `ferrum-alloy`, `ferrum-alloy-telemetry`, `ferrum-alloy-edge`, `ferrum-alloy-diagnostics`, and `ferrum-alloy-cli`, and the `ferrum-alloy` command, are working names. On 2026-09-27 and again on 2026-10-29, the crates.io API returned 404 for all five crate names. These checks reserve nothing: someone else may publish crates under those names before an approved Alloy publication, so check again immediately before a publish. On crates.io a name is owned by whoever publishes it first, and its usage policy forbids squatting; holding a name means publishing, which this decision does not authorize.
- **Naming concerns.** Related names already exist on crates.io (checked 2026-10-29). `ferrum` is a Rust web framework with no release since 2018 (0.2.1). An unrelated LLM inference project publishes at least twenty `ferrum-*` crates, including `ferrum-cli` and `ferrum-server`. `alloy` and its `alloy-*` crates are a widely used Ethereum toolkit. Outside crates.io, Grafana Alloy is an OpenTelemetry collector distribution, close to Alloy's own observability domain. None of these occupies the five exact crate names; whether any of them blocks or confuses Alloy's names is a question for the trademark search below.
- **Trademark.** No trademark search for "Ferrum Alloy" or the crate and command names has been done. It needs a qualified search, not repository research.
- **Registry and license.** Whether crates licensed PolyForm Noncommercial 1.0.0 go to crates.io, to another registry, or nowhere. The manifests declare `license = "PolyForm-Noncommercial-1.0.0"` (an SPDX identifier) and ship `LICENSE-COMMERCIAL.md` alongside; an SPDX expression cannot name the commercial license, so decide whether that is how the dual licensing is presented.
- **License expression for vendored code.** `ferrum-alloy` packages Swagger UI 5.33.0 (`assets/swagger-ui/`). Checked on 2026-10-29: Swagger UI is Apache-2.0 with its `NOTICE`, and `swagger-ui-bundle.js.LICENSE.txt` lists MIT components (React among them), ieee754 under BSD-3-Clause, and DOMPurify 3.4.13 under Apache-2.0 or MPL-2.0. The repository README already excludes these files from Alloy's licensing. For a registry release, the `ferrum-alloy` manifest's `license` should become `PolyForm-Noncommercial-1.0.0 AND Apache-2.0 AND MIT AND BSD-3-Clause`, taking DOMPurify under Apache-2.0, so the manifest does not claim the vendored files are PolyForm-licensed. The `openapi-ui` feature compiles in the bundle, the stylesheet (which carries a normalize.css MIT banner), and the bundle's third-party license file, but not Swagger UI's own `LICENSE` and `NOTICE`, so whoever distributes a binary built with that feature must ship those two files with it.
- **Product homepage URL.** The manifests declare only `repository`. Decide whether the crates get a separate `homepage`, and which URL.
- **Publisher.** Who owns the registry entries and how publishing is authenticated.

This page records that [distribution decision](#distribution-decision), the [stability policy](#stability-policy) that applies from 1.0.0 onward, what CI already checks, the checklist a release commit must satisfy, and the [deferred registry decisions](#deferred-registry-decisions) that must be settled if the owner ever revisits it.

## Distribution decision

**Decision (owner, 2026-10-29): Git-only distribution** ([#24](https://github.com/ferrum-edge/ferrum-alloy/issues/24)). This is Alloy's distribution model for 1.0 and the 1.x line:

- No Alloy crate is published to crates.io or to any other registry. Every crate keeps `publish = false`.
- The license is unchanged: PolyForm Noncommercial 1.0.0, with commercial licensing in `LICENSE-COMMERCIAL.md`. Vendored Swagger UI keeps its own terms.
- Consumers depend on Alloy by git branch, tag, or revision, or by path, as [getting started](getting-started.md) describes. `ferrum-alloy new` keeps writing a git dependency, on branch `main` by default, or a path dependency with `--alloy-path`.
- The `Package dry run` job stays. It keeps the crates packageable so that a later registry decision does not start from scratch, and it never uploads anything.

This decision does not authorize publishing, creating registry accounts or API tokens, reserving names, or changing the license. A Git release is a tag on a commit that satisfies the [release checklist](#release-checklist), with its release notes in a GitHub release for that tag; tagging still needs the owner's approval.

Revisiting the decision is a new owner decision. It requires every item under [deferred registry decisions](#deferred-registry-decisions), and every registry release, not only the first, must complete the checklist items marked *registry only*.

## Stability policy

From 1.0.0 onward, Alloy releases follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html), as Cargo applies it to Rust crates ([Cargo SemVer compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)). Until then, the pre-1.0 rule in the [release checklist](#release-checklist) applies: a breaking change bumps the minor version.

**One exception takes precedence over every other rule in this policy:** the [security exception](#security-exception). Where this page says something happens "only in a major release" or that a release line receives only patch releases, that holds except under the security exception.

### Versions and releases

- The five crates share one version (`workspace.package.version`) and are released together as one Git tag, `vX.Y.Z`, on a commit that satisfies the [release checklist](#release-checklist). A breaking change to a covered surface of any crate makes the next release a major release of all five.
- **Major** (`X`): any breaking change to a [covered surface](#what-the-version-covers), including an upgrade of a [public dependency](#public-dependencies) across a semver-incompatible version and the removal of a deprecated item (except under the [security exception](#security-exception)).
- **Minor** (`Y`): backward-compatible additions (new public items, new optional Cargo features, new CLI commands or flags, new configuration keys whose default keeps existing behavior, new optional properties in a wire contract), deprecations, and MSRV raises.
- **Patch** (`Z`): bug fixes, security fixes, documentation, and dependency updates that change no covered surface.
- Changes to the [Edge-mirrored manifest admission checks](#service-manifest-layers) ship only in minor releases, under the rule in that section.
- Only tagged releases carry these promises. Commits on `main` between releases carry none, including the `main` branch that `ferrum-alloy new` writes into a starter by default; pin a tag (`--alloy-tag`) or a revision instead.
- Because Alloy is distributed from Git, Cargo never moves a dependency from one tag to another: `cargo update` does not pick up a newer compatible release. Upgrading means changing the `tag` in your `Cargo.toml`. Within 1.x that is a compatible upgrade under the rules below.

### What the version covers

1. **The public Rust API** of the five crates: every public item reachable from the crate roots of `ferrum-alloy`, `ferrum-alloy-telemetry`, `ferrum-alloy-edge`, and `ferrum-alloy-diagnostics`, under every combination of their documented Cargo features, together with the feature names themselves and each crate's default feature set. `ferrum-alloy-cli` has no library target; its covered surface is the command line (item 2). A change is breaking when the Cargo SemVer reference classifies it as major. Adding a variant to a `#[non_exhaustive]` enum, or a field to a `#[non_exhaustive]` struct, is a minor change. Removing a feature, removing anything from a default feature set, or adding anything to one is a major change.
2. **The `ferrum-alloy` command line**: command and subcommand names, flags and arguments and their meaning, the environment variables the CLI reads, the JSON documents written with `--format json` (each is its own CLI contract: for example, `diagnose --format json` writes an envelope with `claimed_verification`, `warnings`, and `report`, whose `report` member is a `ferrum.diagnostic_report` v1 document; `diagnose --list-traces` writes `trace_ids`; `check` and `version` write their own objects; members may be added in a minor release), and the exit codes: `0` success, `1` I/O or process failure, `2` rejected arguments (usage error), `3` invalid input (configuration, manifest, report, name, or path, including errors reported by `check`), and `4` drift found by `--check`. Existing exit codes keep their meaning; a new code may be added in a minor release only for a new command or flag.
3. **Configuration**: the TOML keys, the `FERRUM_ALLOY_*` environment variables, and every other environment variable [configuration](configuration.md) documents as read by Alloy or the CLI, whatever its prefix (today `RUST_LOG` and the `OTEL_*` variables in its tables), together with their documented precedence and defaults. A configuration that a 1.x release accepts is accepted, with the same meaning, by every later 1.x release; that includes which documented variables Alloy honors, when it falls back to them (for example `RUST_LOG` only when `logging.filter` is unset, and the OTLP endpoint variables, which Alloy validates itself before the exporter uses them, only when `otlp.endpoint` is unset), and that Alloy's own settings take precedence over them. A variable documented as having no effect starts to have one only in a major release. How a value is interpreted once it is handed to an upstream library is delegated and follows that library's own policy: the `RUST_LOG` directive syntax (`tracing-subscriber`'s `EnvFilter`), and the OTLP header, compression, and resource-attribute variables that the OpenTelemetry SDK and exporter read. When an Alloy release upgrades such a library and that interpretation changes, the release notes say so. Changing a documented default in a way that changes an existing deployment's behavior is a major change, except under the [security exception](#security-exception).
4. **Generated projects**: the project layout `ferrum-alloy new` writes (the file and directory names that Alloy's commands and the generated CI rely on, such as `alloy.toml` and `ferrum-service.toml`) and the `ferrum-service.toml` format, which is the TOML form of `ferrum.service_manifest` v1 (see [service manifest layers](#service-manifest-layers)). An upgrade never rewrites a generated project, and a generated project uses only the public API, so item 1 covers its code.
   - **Schema migrations are forward-only from 1.0.0.** Alloy itself creates no database schema; `postgres::migrate` runs the service's own embedded migrations. The PostgreSQL starter ships migrations under `migrations/`. From 1.0.0 onward, a starter schema change meant for existing installations ships as a new, higher-numbered migration, and a starter migration that has shipped in a release is never edited, because SQLx records a checksum of every applied migration and refuses to migrate when an applied file has changed. Once generated, a service owns its migrations, including the starter's; Alloy recommends the same forward-only rule for them.
5. **The wire contracts Alloy owns** in [ferrum-contracts](https://github.com/ferrum-edge/ferrum-contracts) ([ownership](https://github.com/ferrum-edge/ferrum-contracts/blob/main/docs/ownership.md)): `ferrum.diagnostic_report` v1 (source of truth `contracts/diagnostics/diagnostic-report.v1.schema.json`; written as a standalone document by `diagnose --write-report` and by diagnostic retrieval, carried as the `report` member of the `diagnose --format json` envelope, and read by `diagnose --input`) and `ferrum.service_manifest` v1 (source of truth `crates/ferrum-alloy-edge/src/manifest.rs`). Every 1.x release writes and reads v1 of both. Changes within v1 follow ferrum-contracts' [versioning rules](https://github.com/ferrum-edge/ferrum-contracts/blob/main/docs/versioning.md) (for example, a new optional property), land in ferrum-contracts first, and may ship in a minor release. A new major version of either contract, dropping v1, or changing what a v1 value means ships only in a major release. Contracts Alloy consumes but does not own (Edge's vocabularies and `diagnostic_ref`) move with the [Edge support policy](#ferrum-edge-support); adopting a newer `contracts-edge-*` pin is not by itself a breaking change.
6. **Operational surface**: the paths of Alloy's built-in endpoints (`/livez`, `/readyz`, `/health`, `/metrics`, and the other routes documented in [configuration](configuration.md) and [security](security.md#management-surface)), the names and labels of the metrics Alloy exports, the Problem Details `type` and status of each documented framework error, and the `alloy.*` telemetry attributes defined in [measurement semantics](measurement-semantics.md).

### Service manifest layers

A `ferrum-service.toml` is checked in two layers, and only the first is fixed for the whole 1.x line:

1. **Alloy-owned v1 parsing and semantics** are stable for all of 1.x: the keys, their types and meanings, defaults, and Alloy's own validation rules (for example the literal path grammar, which is a stricter subset of what Edge admits). A manifest that satisfies this layer in one 1.x release satisfies it, with the same meaning, in every later 1.x release; whether it is also admitted for export is layer 2.
2. **Edge-mirrored export admission** consists of the checks that copy a supported Ferrum Edge release's own admission rules so that an export never produces configuration Edge would refuse: for example, the `gateway.otel_endpoint` plaintext rule (Edge #6659), Edge's limits on timeouts, health-check intervals, resource-ID, `listen_path`, path, and host lengths, and the path forms Edge refuses. They run in `ServiceManifest::validate` (also called by `ServiceManifest::from_toml`), so they apply wherever a manifest is loaded: `ferrum-alloy edge export` and `ferrum-alloy openapi export --manifest`. They may change when the [Edge support window](#ferrum-edge-support) rolls, only in a minor release, and only to match what the supported Edge releases themselves refuse (tightened when a newly supported release refuses a shape, loosened when no supported release refuses it any longer). The release notes list each change with the manifest shapes it affects.

### What the version does not cover

- Items marked `#[doc(hidden)]`, even when they are `pub`.
- Test utilities: test modules and helpers, fixtures and snapshot files (`*.expected.txt`, `*.edge.yaml`), `UPDATE_SNAPSHOTS`, the `ci/` scripts and their tests, and the fuzz targets in `fuzz/`.
- Benchmark tooling and results: `examples/bench`, its budgets, the hosted benchmark scripts and workflows, and every benchmark number.
- Generated code internals: the contents of the files a starter is generated with (example handlers, tests, README, the generated CI workflow, and the dependency versions it pins), apart from the migration rule in item 4, and the exact text of `openapi export` and `edge export` output. Their layout (item 4) and their formats are covered; that `edge export` output validates against each supported Edge release is the [Edge support policy](#ferrum-edge-support).
- The examples under `examples/`, the repository's CI workflows, and other repository tooling.
- Human-readable text: log messages, CLI output with `--format human`, error and warning messages, the `detail` of Problem Details responses, and diagnosis explanations.
- Performance and resource use, beyond documented limits.
- Behavior behind unsupported Edge releases or unreleased Edge `main`.
- Behavior that contradicts the documentation. Fixing it is a bug fix, released in a patch or minor release with a changelog entry that says who is affected and how to adapt.

Every other dependency is private: Alloy may upgrade or replace it, across incompatible versions too, in a minor or patch release, as long as no covered surface changes.

### MSRV

The minimum supported Rust version is **1.94** (`rust-version` in `Cargo.toml`, set by sqlx 0.9). The `MSRV (1.94)` CI job builds every crate, target, and feature combination it checks with that toolchain and the committed `Cargo.lock`. From 1.0.0 onward, raising the MSRV ships in a minor release, never in a patch release, and the release notes call it out. A project that resolves newer versions of Alloy's dependencies than the committed lockfile may need a newer compiler than the MSRV.

### Ferrum Edge support

Each Alloy release supports the latest Ferrum Edge release and the release before it: the two releases in `edge_support.tested` of [compatibility.json](compatibility.json) at that release's commit, which CI tests on every run ([compatibility](compatibility.md#supported-edge-releases)). The window rolls forward as Edge publishes releases; moving it is not a breaking change (manifest checks that mirror Edge change with it, under the [manifest layer rule](#service-manifest-layers)), and the Alloy release that moves it records the change in its changelog and in [compatibility](compatibility.md). Alloy does not refuse to run behind other Edge releases, but claims nothing for them.

### Deprecation

- A covered surface is deprecated in a minor release before it is removed. Rust items get `#[deprecated(since = "1.Y.0", note = "...")]` naming the replacement; a deprecated CLI command or flag keeps working and prints a warning to standard error; a deprecated configuration key keeps being accepted and is reported as a configuration warning at startup and by `ferrum-alloy check`. Wire-contract fields follow ferrum-contracts' versioning rules.
- The changelog lists every deprecation under "Deprecated", with its replacement.
- Where a replacement exists, it ships in the same release as the deprecation or earlier, and the item stays deprecated through at least one 1.x minor release before the major release that removes it.
- Deprecated surfaces keep working for the rest of the 1.x line and are removed only in a major release. A new deprecation warning is not a breaking change, even for builds that deny warnings.

### Support window for 1.x

- During 1.x, fixes land on `main` and ship in the next 1.x release. Only the latest 1.x release is supported; earlier 1.x releases receive no backports, because upgrading within 1.x is compatible.
- After 2.0.0 is released, the last 1.x minor line receives security fixes for six months from the 2.0.0 release date, as patch releases (or, under the security exception, as one further minor release). It receives no other changes.
- 0.x tags receive no fixes once 1.0.0 is released.

#### Security exception

This is the only exception to the stability policy, and it takes precedence over every other rule on this page, including the rules that something happens only in a major release and the patch-only window after 2.0.0. If a vulnerability cannot be fixed without a breaking change, including an upgrade of a public dependency across an incompatible version, the fix ships in a new 1.x minor release. During the six months after 2.0.0, that minor release (for example 1.(Y+1).0 after 1.Y.Z) becomes the last 1.x minor line for the rest of the same window; the window is not extended. The security advisory and the release notes state exactly what breaks and how to migrate. See [SECURITY.md](../SECURITY.md).

Every pull request is reviewed against this policy. CI's `Semver checks` jobs supplement that review: from the first `v1.*` tag on, `cargo-semver-checks` compares each library crate's public Rust API with the newest `v1.*` release tag reachable from the commit, under default features, no default features, all features, and each feature alone, and fails on a change that a 1.x minor release may not make; the jobs also fail when a crate's default feature set changes in either direction, which cargo-semver-checks alone reports only for removals. Before that tag exists the jobs are skipped with a notice. They cannot see the command line, configuration, wire formats, or behavior, so review remains the gate.

## What CI checks now

The `Package dry run` job in `.github/workflows/ci.yml` runs on every pull request and every push to `main`. `cargo package` only builds `.crate` archives under `target/package/`; it never uploads anything.

1. **Package.** `cargo package --locked --no-verify --exclude-lockfile` for the five crates: `ferrum-alloy-diagnostics`, `ferrum-alloy-telemetry`, `ferrum-alloy-edge`, `ferrum-alloy`, and `ferrum-alloy-cli`. The examples are not packaged.
2. **Packaged files.** Every archive contains `Cargo.toml`, `README.md`, `LICENSE`, and `LICENSE-COMMERCIAL.md`, and the license files match the repository's byte for byte. The CLI archive contains every committed file under `crates/ferrum-alloy-cli/templates/`, including `templates/base/.github/`, and the `ferrum-alloy` archive every committed file under `crates/ferrum-alloy/assets/`.
3. **Packaged sources build on their own.** The job unpacks the archives into a new workspace outside the repository, with a `[patch.crates-io]` entry that points each crate at its unpacked archive, and runs `cargo check` with all features and with default features. It fails if any `ferrum-alloy*` crate resolves from a registry instead of the unpacked archives. This catches a file a crate needs but does not package, such as a template compiled in with `include_str!`.
4. **Container images.** The repository does not publish a container image. The `Ferrum Edge end-to-end` job builds the example stack's images from `examples/edge-observability/Dockerfile` and its compose file; keep that build passing when those inputs change.

The `Package dry run` job name is a stable CI check. Extend that job if more publishable crates are added; do not create a second packaging job.

### Why `--no-verify --exclude-lockfile`

The crates depend on each other, and none of them is in a registry. `cargo package` writes a `Cargo.lock` into each archive and, unless `--no-verify` is given, builds each archive; both resolve the sibling crates. Packaging with a lockfile or with verification needs a registry the crates may be published to, and `publish = false` rules that out: Cargo resolves workspace siblings through a temporary local registry, but it does not add `publish = false` packages to it, so it would look for them on crates.io and fail (or, if someone published a crate with the same name, resolve to that crate). `--exclude-lockfile` and `--no-verify` skip both resolutions. Step 3 then does the verification that `--no-verify` skips, with an explicit patch that can never resolve to a registry crate.

Once publishing is approved and `publish = false` is removed, `cargo package --workspace` resolves the siblings through its local registry, and the job can drop both flags.

### Package contents

Each crate declares an `include` list in its `Cargo.toml`: `src/`, its `README.md`, and the two license files; the CLI also includes `templates/`, `ferrum-alloy-edge` includes `fixtures/` (the Edge parity fixtures its unit tests read, which `ci/edge_parity.py` also uses), and `ferrum-alloy` includes `assets/`, the vendored documentation UI (feature `openapi-ui`) with its Apache-2.0 `LICENSE`, `NOTICE`, bundled notices, and hash manifest. Integration tests are not packaged, because they read fixtures from outside the crate (`contracts/`, `docs/`, the examples). Some unit tests in `src/` of `ferrum-alloy-diagnostics`, `ferrum-alloy` and the CLI also read repository fixtures, so they run only in the repository; the Edge parity unit tests of `ferrum-alloy-edge` read its packaged `fixtures/`. The `LICENSE` and `LICENSE-COMMERCIAL.md` files in each crate directory are symbolic links to the repository's, and Cargo packages their contents.

The internal workspace dependencies carry `version = "0.1.0"` next to `path`, so that the packaged manifests contain a registry dependency on each sibling. Builds in this repository still use the path.

## Release checklist

A release commit must satisfy every item. Record the evidence in the release notes. Under the [Git-only decision](#distribution-decision), a release is a Git tag and the items marked *registry only* do not apply. They apply to every registry release; their one-time configuration changes (removing `publish = false`, dropping the package flags, the license exceptions, and the manifest license expression) are made by the first.

- [ ] **Owner approval.** The owner has approved this release. For a registry release, the [deferred registry decisions](#deferred-registry-decisions) are also recorded.
- [ ] **Version.** All five crates share `workspace.package.version`. Bump it and the `version` of every internal entry in `[workspace.dependencies]` together. Before 1.0, a breaking change bumps the minor version, and any other change bumps the patch version. From 1.0.0 onward, the version follows the [stability policy](#stability-policy).
- [ ] **Changelog.** [CHANGELOG.md](../CHANGELOG.md) lists the user-visible changes, including changes to configuration (`docs/configuration.md`), the diagnostic evidence schema, and Edge contracts. Review its Unreleased entries and create the release entry for the approved version. From 1.0.0 onward, it also lists every deprecation and, for a major release, every breaking change with its migration.
- [ ] **MSRV.** The release notes state the MSRV (`rust-version`, currently 1.94, set by sqlx 0.9), and the `MSRV (1.94)` job passes on the release commit. An MSRV increase is called out as a change; from 1.0.0 onward it is never made in a patch release.
- [ ] **Compatibility.** `docs/compatibility.md` and `docs/compatibility.json` describe the tested matrix on the release commit: the Edge support window (the latest Edge release and the previous one), the pinned images, and the component versions.
- [ ] **Edge contract pin.** If the Edge contract baseline changes, `contracts/ferrum-contracts/PIN` names the matching published `contracts-edge-*` tag and commit, its file hashes match the vendored files, and the pairing checks pass. Update `docs/compatibility.json`, the compatibility page, `contract::{EDGE_RELEASE, EDGE_SOURCE_COMMIT}`, fixture headers, and the CLI pairing assertion together. See [compatibility](compatibility.md#pairing-rules) and [the contract pin procedure](../contracts/README.md#ferrum-contracts-pin).
- [ ] **MCP bridge vocabulary parity** (at the next contracts re-pin). ferrum-contracts#96 publishes Edge's `mcp-openapi-bridge` vocabulary (`vocabularies/mcp-openapi-bridge.json`, schema `vocabulary-mcp-openapi-bridge` v1). When the pin moves to the first `contracts-edge-*` tag that contains it, vendor the vocabulary with its schema and fixtures and add a pairing test that compares the constants Alloy copies in `crates/ferrum-alloy-edge/src/agents.rs` with it: the namespace and tool-name byte limits, the document-level and per-operation `x-ferrum-mcp` keys, the reserved bridge header names and prefixes, the unbridged methods, and the `max_structured_content_bytes` bound. Until then those constants are checked only by Alloy's unit tests and the `edge-config` job's `POST /api-specs` step.
- [ ] **Security review.** Review the release diff against [the security model](security.md), including dependency changes and security-relevant behavior. Record the reviewer and evidence with the release notes; resolve or explicitly disposition findings before release.
- [ ] **Benchmark baseline.** Since the owner closed #15 as not planned (2026-11-04), the [regression gate](benchmarks.md#regression-gate) is diagnostic only and not a release gate: the release notes state that no regression-gate run is claimed, or record a run if one was made. If the owner reinstates the gate, it must pass for the release commit, on a calibrated CPU model, with the run recorded with its host and limits; if the harness, a workload, the runner image, or the toolchain changed since the calibration, recalibrate first.
- [ ] **CI evidence.** Every job in `.github/workflows/ci.yml` passed on the release commit itself, including `Package dry run`, both `Ferrum Edge end-to-end` slots, `Generated projects`, `PostgreSQL integration`, `Dependency policy`, `MSRV`, and `Fuzz smoke`. Link the run in the release notes.
- [ ] **SBOM and provenance.** Generate an SPDX or CycloneDX SBOM for the exact release commit and attach it to the tag's GitHub release. When the release ships build artifacts (for a registry release, the `.crate` archives), also produce build provenance from the trusted CI workflow for that same repository, ref, and commit, verify that its subject digests match the released artifacts, and link it from the release notes. A Git release without build artifacts has no provenance subject. Do not claim an attestation that was not produced and verified.
- [ ] **Generated projects.** `ferrum-alloy new` writes a git dependency on Alloy that follows `main` by default (`--alloy-git`, `--alloy-branch`, `--alloy-tag`, or `--alloy-rev` change it). The release notes show `ferrum-alloy new <name> --alloy-tag <tag>` for a starter pinned to this release. For a registry release only, decide whether starters switch to a registry dependency, and update the templates and the generator tests if so.
- [ ] **License policy** (*registry only*). `cargo deny check` skips the five crates' own `PolyForm-Noncommercial-1.0.0` license only while they are private: `[licenses.private] ignore` in `deny.toml` skips a crate whose `publish` is `false` (or an empty list), or lists only registries that `[licenses.private] registries` also names. A crate published to crates.io or another public registry is not private, so in the first registry release PR add a license exception for each of the five crates. Only for a private alternate registry can the crates instead set `publish = ["<registry>"]` and list the same name under `[licenses.private] registries`; setting `registries` alone, with `publish` removed, is not enough. In the same PR, give `ferrum-alloy` its own `license`, overriding `license.workspace` for that crate only, with the expression recorded under [deferred registry decisions](#deferred-registry-decisions), so its manifest does not claim the vendored Swagger UI files are PolyForm-licensed.
- [ ] **Merge and tag.** The release commit is a GitHub merge commit whose second parent is the reviewed PR head. Confirm the `push` CI run for that merge commit is green before creating the release tag. Tag that merge commit itself, never the PR head or a commit that has not passed push CI; record the tag and CI run in the release notes.
- [ ] **Publish** (*registry only*). In the release PR, remove `publish = false` (or restrict it to the chosen registry) and drop `--no-verify --exclude-lockfile` from the package job, so that push CI on the merge commit packages exactly what will be published. Publish only after **Merge and tag**: from a Linux or macOS checkout (`core.symlinks=true`) of the tagged merge commit whose push CI, including `Package dry run`, passed; a Windows checkout turns the symlinked license files into 13-byte text files. Check that each packaged `LICENSE` matches the root file before `cargo publish`, and publish in dependency order: diagnostics, telemetry, edge, `ferrum-alloy`, the CLI. A published version cannot be replaced, so never publish from a PR head or an untagged commit.

## Deferred registry decisions

The Git-only decision sets these aside; it does not settle them. Each one must be decided and recorded here before any registry publication. The evidence below was refreshed on 2026-10-29. It is research, not legal clearance or a name reservation.

- **Crate and command names, and registry availability.** `ferrum-alloy`, `ferrum-alloy-telemetry`, `ferrum-alloy-edge`, `ferrum-alloy-diagnostics`, and `ferrum-alloy-cli`, and the `ferrum-alloy` command, are working names. On 2026-09-27 and again on 2026-10-29, the crates.io API returned 404 for all five crate names. These checks reserve nothing: someone else may publish crates under those names before an approved Alloy publication, so check again immediately before a publish. On crates.io a name is owned by whoever publishes it first, and its usage policy forbids squatting; holding a name means publishing, which this decision does not authorize.
- **Naming concerns.** Related names already exist on crates.io (checked 2026-10-29). `ferrum` is a Rust web framework with no release since 2018 (0.2.1). An unrelated LLM inference project publishes at least twenty `ferrum-*` crates, including `ferrum-cli` and `ferrum-server`. `alloy` and its `alloy-*` crates are a widely used Ethereum toolkit. Outside crates.io, Grafana Alloy is an OpenTelemetry collector distribution, close to Alloy's own observability domain. None of these occupies the five exact crate names; whether any of them blocks or confuses Alloy's names is a question for the trademark search below.
- **Trademark.** No trademark search for "Ferrum Alloy" or the crate and command names has been done. It needs a qualified search, not repository research.
- **Registry and license.** Whether crates licensed PolyForm Noncommercial 1.0.0 go to crates.io, to another registry, or nowhere. The manifests declare `license = "PolyForm-Noncommercial-1.0.0"` (an SPDX identifier) and ship `LICENSE-COMMERCIAL.md` alongside; an SPDX expression cannot name the commercial license, so decide whether that is how the dual licensing is presented.
- **License expression for vendored code.** `ferrum-alloy` packages Swagger UI 5.33.0 (`assets/swagger-ui/`). Checked on 2026-10-29: Swagger UI is Apache-2.0 with its `NOTICE`, and `swagger-ui-bundle.js.LICENSE.txt` lists MIT components (React among them), ieee754 under BSD-3-Clause, and DOMPurify 3.4.13 under Apache-2.0 or MPL-2.0. The repository README already excludes these files from Alloy's licensing. For a registry release, the `ferrum-alloy` manifest's `license` should become `PolyForm-Noncommercial-1.0.0 AND Apache-2.0 AND MIT AND BSD-3-Clause`, taking DOMPurify under Apache-2.0, so the manifest does not claim the vendored files are PolyForm-licensed. The `openapi-ui` feature compiles in the bundle, the stylesheet (which carries a normalize.css MIT banner), and the bundle's third-party license file, but not Swagger UI's own `LICENSE` and `NOTICE`, so whoever distributes a binary built with that feature must ship those two files with it.
- **Product homepage URL.** The manifests declare only `repository`. Decide whether the crates get a separate `homepage`, and which URL.
- **Publisher.** Who owns the registry entries and how publishing is authenticated.

# ADR 0007: Prove Edge integration with a pinned real gateway

**Status:** Accepted (2026-09-26). The single pinned release below is superseded by the two-release matrix in `docs/compatibility.json` (`edge_support.tested`). Amended 2026-09-27 with the attempt and connection cases, 2026-10-01 for Edge v0.9.9's per-attempt CLIENT spans and diagnostic references, and 2026-10-01 for Edge v0.9.10. The 2026-10-04 adoption candidate rolls the existing latest-plus-previous window to v0.9.11/v0.9.10, with static source re-audit and fresh hosted validation pending. Older release examples below are historical; the strict attempt/reference assertions remain unchanged and run for both current matrix entries.

## Context

A header-echo mock can pass while the real gateway behaves differently: which span becomes the parent, retry behavior, `-1` sentinels, OTLP encoding, or backend mTLS details.

## Decision

- CI runs a published Ferrum Edge image pinned by digest (v0.9.7, the same digest Ferrum Foundry pins), an OpenTelemetry Collector pinned by digest (contrib 0.161.0), and the Alloy example, on one compose network.
- Edge configuration is generated by `ferrum-alloy edge export` and checked with `ferrum-edge validate` before use. `gen-e2e-edge-config` appends three test-only proxies (below) using documented Edge proxy fields, and it stops the build unless its rendering of the service's own proxy, upstream, and plugins is byte-identical to the CLI's output. Demo certificates are generated at build time. No host bind mounts are used, so the stack runs the same under colima and in CI.
- `edge-e2e` asserts facts from the collector's exported spans:
  - the Alloy SERVER span is under the Edge SERVER span that Edge echoed to the client: its direct child for legacy v0.9.8 input, and the child of one Edge attempt CLIENT span on supported v0.9.9 and v0.9.10, which hand the backend that span as its `traceparent` parent;
  - Alloy accepted that context only from the verified SPIFFE identity;
  - Edge's request id was reused;
  - the operation span nests under the service span;
  - a streamed span covers its body;
  - direct access is rejected;
  - offline diagnosis stays at `likely`.
- It also drives the attempt and connection cases. Every fault is produced inside the compose network, never by changing the host's network:

  | Case | Fault and Edge configuration | Asserted on spans and diagnosis |
  |---|---|---|
  | Retry | Alloy's `/flaky/{key}` answers `503` to the first request for a key. Proxy `e2e-retry` has `retry: {max_retries: 1, retryable_status_codes: [503], retryable_methods: [GET]}` and Edge's default 100 ms fixed backoff. | One Edge SERVER span and two Alloy SERVER spans under it (directly for legacy v0.9.8 input; on v0.9.9 and v0.9.10 each through its own attempt span, numbered `1` and `2`), answering `503` then `200`, each with the gateway's trace context and request id. Edge `backend_ttfb` is at least the sum of both attempts' time to headers plus the backoff. Diagnosis reports `alloy.gateway.multiple_service_attempts`, makes no gateway-wide comparison of gateway and service timings, and confirms nothing. Values are scoped to attempts `1` and `2` only from attempt spans, and to no attempt on v0.9.8. |
  | Cold and reused connection | Proxy `e2e-reuse` reaches Alloy through the `alloy-reuse` network alias, which no other proxy uses, with Edge pool warmup off. A middleware over Alloy's whole application router counts every request per connection (main-proxy traffic and health checks included), and `/conn` reports the connection a request arrived on and how many earlier requests it carried. | The first request's connection carried no earlier request; a later one reuses a connection. Each has one Edge SERVER span and one Alloy SERVER span under it. Neither SERVER span carries a timing outside the documented request-scoped set, every observation is in the catalog, and nothing is confirmed. A connection setup appears only as Edge v0.9.9 measured it on an attempt span, scoped to that attempt, and never on the reused request. An unattributed interval must cite that setup or the reuse, or list gateway connection setup timing as missing: setup Edge did not measure stays unmeasured, never zero. |
  | Concurrent HTTP/2 streams | Six concurrent requests through `e2e-reuse`, with one Edge HTTP/2 connection per backend host. Alloy's `/gather/6` holds each request until all six are inside the handler. | Every request saw all six in flight, the requests shared fewer than six connections, each stream has one Edge SERVER span and one Alloy SERVER span under it with `network.protocol.version = 2`, the Alloy spans overlap in time (one process, one clock), and no setup is charged to any of them. |
  | Client cancellation mid-body | The driver reads the first frame of the 4 s `/events/long` stream through Edge and closes its connection. | Edge records `gateway.client.disconnected=true`. Exactly one Alloy SERVER span, with outcome `cancelled`, a body that ended before 3 s, and one `alloy.response.body_incomplete` finding that is not confirmed. |
  | Refused connection | Proxy `e2e-refused` points at a port on the Alloy container where nothing listens. When Edge echoes no `traceparent`, the driver takes the newest Edge SERVER span for the proxy, so a rerun does not match an earlier run's trace. | `X-Gateway-Error: connection_failure` on a 5xx, one Edge SERVER span with `gateway.error.class` and no Alloy span, and a diagnosis with `alloy.edge.gateway_error_token` (`likely`, not proof that the service is down) and `alloy.edge.gateway_error_class`, nothing confirmed. On both supported releases, with `FERRUM_DIAGNOSTIC_REFS=errors`, the response also carries a well-formed `X-Ferrum-Diagnostic-Ref` that diagnosis records as `alloy.edge.diagnostic_ref` (`likely`). |

- Both supported releases run every case, including the diagnostic-reference checks. The proxy and retry fields, pool environment variables, `connection_failure` token, and span attributes used are the same in v0.9.9 and v0.9.10. The parentage checks also accept legacy v0.9.8 input: an Alloy SERVER span directly under the Edge SERVER span for v0.9.8, or under one Edge attempt CLIENT span that is itself under it for v0.9.9 and v0.9.10. The retry case is strict per release: the driver resolves the release from `EDGE_IMAGE` against `docs/compatibility.json` and requires attempt spans numbered `1` and `2` on v0.9.9 and v0.9.10 and none on v0.9.8.
- The collected spans, summary, diagnosis, and service logs are uploaded as CI artifacts.

## Consequences

- Moving to a new Edge release means updating the digest, re-running the contract inventory, and re-running this job.
- The stack sets `FERRUM_POOL_WARMUP_ENABLED=false` and `FERRUM_POOL_HTTP2_CONNECTIONS_PER_HOST=1` so connection identity is deterministic. Edge's defaults (warmup on, 2 to 8 connections per host) are not what this job exercises. It also sets `FERRUM_DIAGNOSTIC_REFS=errors` (Edge's default is `off`) and keeps the admin listener off, so references are minted but never looked up.
- Connection reuse is observed from Alloy's side of the connection, because Edge v0.9.8 exports no connection identity or setup timing. On supported v0.9.9 and v0.9.10 the attempt span's connection attributes are also read, and must agree with Alloy's view of a reused connection.
- Not covered: an upstream reset after the connection is established (only a refused connection is exercised), and per-attempt timing on v0.9.8, which does not record it.

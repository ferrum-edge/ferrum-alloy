# Implementation status

This page records what exists and what evidence backs it. "Tested" means an automated test in this repository exercises the behavior. Local results are from macOS arm64 on 2026-09-26. Hosted CI results are in the CI checks and are not restated here.

Everything is pre-release. No crate is published (`publish = false` everywhere).

## Partial

| Area | State |
|---|---|
| Benchmarks | A harness exists (`examples/bench`). Local, same-host, interleaved runs on a shared machine measured small-payload HTTP/1.1 throughput and latency, and a before/after comparison of span-record batching; see [benchmarks.md](benchmarks.md). Large payloads, h2c, TLS, CPU time, memory, allocations, and a healthy Collector were not validly measured. No regression budget is enforced in CI. |
| Platforms | Only macOS arm64 was run locally. Linux x86_64, macOS, and Windows results come from hosted CI. |
| Ferrum Edge versions | The latest release and the one before it (v0.9.10 and v0.9.9) are tested. Older releases, including v0.9.8, are unsupported. A scheduled workflow proposes new releases. |
| Service manifest | `ferrum.service_manifest` v1 is PROPOSED. Edge does not consume it. The optional `[agents]` section is read only by `openapi export`; the shared `service-manifest` v1 schema in ferrum-contracts does not include it yet (see [contracts](../contracts/README.md#service-manifest-schema)). |
| Anvil interoperability | The finding shape is a superset of Anvil's `DiagnosticFinding`. The shared schema is vendored and pinned from `contracts-edge-0.9.9-r2`, but its shared status is still PROPOSED and no Anvil import exists. The G01 diagnostic reference is released in Edge v0.9.9 (off by default) and absent in v0.9.8. Diagnosis records a reference a client observed (`alloy.edge.diagnostic_ref`, at most `likely`) and resolves it only with explicit admin access and a separate trusted client observation (ADR 0009), following Anvil (ferrum-anvil#271). Confirmation applies only to the bound gateway record's facts, never service timing or offline reports. |

## Not implemented

- Operation-level evidence in live diagnostic reports (`alloy.operation.duration`, `alloy.db.pool_wait`, `alloy.admission.wait`). Live reports carry server-level timing only; OTLP export remains the source for operations.
- Diagnostic retrieval across replicas. Evidence is kept per process.
- OCSP checks for client certificates.
- Watching TLS files for changes. Reloads poll on `server.tls.reload_interval_ms`.
- Scheduled long-running fuzzing. CI runs a 60-second smoke run per target; longer runs are manual (see [testing.md](testing.md)).
- Service-side HTTP/3, gRPC tooling, and WebSocket message tracing.
- Tenant or namespace authorization (application responsibility by design).
- Publishing to crates.io. CI packages the four library crates and the CLI (examples excluded) without publishing, and [release.md](release.md) holds the release checklist and the open owner decisions.
